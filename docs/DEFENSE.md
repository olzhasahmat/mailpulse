| **1:20–1:50** | 3. Решение | Три шага: читает ящики → понимает важность → шлёт важное с кнопкой. Не задерживаться. |

| **3:10–5:00** | 5. Архитектура | **Ядро 40%.** Провести по пути письма. Почему **LangGraph**, а не CrewAI/Parlant. Что компоненты независимы (порты), где сознательный coupling (checkpointer↔Postgres) и почему. |

| **6:20–7:10** | 8. RAG | **25%.** Гибридный поиск (вектор+полнотекст, RRF), почему гибрид. Порог отсечения шума подобран **по evals, не на глаз** — и как настоящая почта показала дыру, которую синтетика не видела. |
| **7:10–7:40** | 9. Мультимодальность | Vision/OCR по скану счёта: в тексте пусто, сумма и срок только на картинке. Vision запускается **только когда нет текстового слоя** (дорого/медленно). |

## Опорные тезисы по решениям (это спрашивают на Q&A — 40%+25%)

Отвечать формулой: **выбор → почему → что рассматривал → чем платим**.

**Почему LangGraph, а не CrewAI/Parlant?**
Процесс детерминированный: проверки → классификация → ветвление → пауза на человека. Нужны явные ветвления, цикл и пауза на часы. CrewAI — про команды агентов с ролями, у нас конвейер. Parlant — про диалоговые гайдлайны, у нас нет чата. Цена: зависимость от API LangGraph, узлы должны переживать повторный запуск после resume.

**Почему один Postgres (pgvector + очередь + чекпоинты), а не Qdrant + Redis/Celery?**
Один компонент в эксплуатации. Письмо и задача на его разбор пишутся в одной транзакции — не бывает письма без задачи. Объём (тысячи писем/день) далёк от пределов Postgres. Цена: очередь без приоритетов; при росте нагрузки polling давит на БД. Qdrant вернём, если A/B покажет выигрыш в retrieval.

**Почему Haiku на классификации, а не Sonnet?**
A/B на 40 письмах: accuracy одинаковая (0.78), а **recall≥2 у Haiku 1.00 против 0.93 у Sonnet** (Sonnet пропустил важное), при вдвое меньшей цене и задержке. Классификация — 90% вызовов, там и экономика.

**Почему температура 0?**
recall≥2 = 1.00 при любой t. Accuracy при t=1.0 на одном прогоне случайно выше — это шум недетерминированных ответов. Берём t=0 ради воспроизводимости. (На Sonnet/Opus температуры нет вообще — там `effort`.)

**Почему MCP, а не обычный API?**
Один и тот же сервер использует наш агент И Claude Desktop — пользователь спрашивает «что бухгалтер писал про акт сверки» и получает ответ по своей почте без отдельного чат-интерфейса. Скоуп по user_id обязателен.

**Почему свой Skill, а не всё в системный промпт?**
Один SKILL.md работает и в Claude Desktop, и в нашем агенте. Тело Skill подставляется только в промпт нужного узла (progressive disclosure) — меньше токенов в каждом вызове.

**Гиперпараметры:** temperature подбирали на Haiku (там она есть), на Sonnet — `effort` и `max_tokens`. Всё экспериментом, не по умолчанию (ADR-014).

**Гипотезы, которые НЕ подтвердились** (это любят спрашивать):
- «Sonnet точнее Haiku» — нет, recall≥2 ниже.
- «Одного порога расстояния хватит, чтобы убрать шум» — нет, короткие письма ложатся близко ко всему; нужны 3 правила.
- «Кэш промпта удешевит классификацию» — нет, у Haiku минимум кэша 4096 токенов, наш промпт короче.

## Q&A: контрольные вопросы менторов и короткие ответы

**Архитектура (40%)**
- *Проведите путь одного запроса.* → IMAP IDLE ловит письмо → в одной транзакции сохраняется + ставится задача → воркер запускает граф (guardrail → RAG → classify → summarize) → карточка в Telegram; нажатие → задача resume → граф продолжается из чекпоинта.
- *Что можно заменить без переписывания?* → порты `Embedder`, `Classifier`, `Retriever`, `MailStore` — реализации меняются, граф нет. В тестах все порты — фейки.
- *Сколько стоит один запрос и как оптимизировали?* → ~$0.008 важное письмо, ~$0.003 шум. Дешёвая Haiku на 90% вызовов, обрезка тела, Batch API для рассылок.
- *Что если основная LLM недоступна?* → fallback на второго провайдера; при отказе обоих — карточка без AI (деградация). При превышении бюджета — всё через Haiku, черновики off.

**LLM-инженерия (25%)**
- *Как эволюционировал промпт?* → classify-v1 (базовый) → v2 (история отправителя) → v3 (RAG-контекст). Версия пишется в `triage_results.prompt_version`, чтобы сравнивать в A/B.
- *Что в golden dataset и как покрывает edge cases?* → 40 писем, 3 языка, фишинг/инъекция, счёт-скан, короткие ответы, маркетинг под личное. По ≥6 на уровень важности.
- *Что метрики НЕ показывают?* → пришло ли уведомление вовремя и полезно ли оно в реальном потоке. Для этого продуктовая метрика «доля черновиков без правок» из `feedback`.
- *Какие edge cases ломают систему?* → короткие письма близки ко всему в RAG (решили 3 правилами); категория — слабое место (0.65), таксономия спорная на границах.

**Обязательные модули (20%)**
- *Покажите MCP-сервер.* → 6 tool'ов, `send_draft` отказывает без одобрения в Telegram. Почему MCP — см. выше.
- *Покажите Skill.* → `email-triage`: правила важности + пограничные случаи; триггеры в описании; подключён и в Claude Code через `.claude/skills`.
- *Где мультимодальность и что было бы потеряно без неё?* → счёт-скан: без OCR сумма и срок не извлекаются вообще.
- *Дашборд LangSmith* → показать трейс одного письма (узлы графа + вызов Claude с токенами и стоимостью).

**Бизнес (5%)**
- *Кто пользователь?* → человек с 3–5 ящиками (личный, рабочий, для регистраций), 80–150 писем/день, важных единицы.
- *Пробовали на реальных людях?* → да, работает на моей настоящей почте: 2 ящика, 165 писем; онбординг через бота протестирован с телефона.

## Подготовка ДО защиты (за 30 минут)

1. `make up` — поднять стек; дождаться, пока воркер прогрузит модель (~30 сек).
2. `cloudflared tunnel --url http://localhost:8000` → вписать URL в `.env` `MINIAPP_URL`, перезапустить бота.
3. Залогиниться в **eu.smith.langchain.com**, открыть проект `mailpulse` в отдельной вкладке.
4. **Записать запасное видео демо (30–45 сек)** — на случай, если IMAP/API/Telegram подведут в момент выступления.
5. Прогнать `make eval-classify` заранее — показывать готовые цифры, а не ждать API вживую.
6. Открыть `docs/MailPulse.pptx` и один раз проговорить доклад по таймеру.
7. Держать под рукой одну команду `make inject-email account=yandex template=invoice` — чтобы за секунду породить свежий трейс на глазах у менторов.

## Главное правило защиты

Менторы оценивают **мышление**, а не идею. На каждый «что» добавляй «почему именно так и что рассматривал». Если не знаешь ответа — честно: «рассматривали X, отказались из-за Y» лучше, чем оправдания. Гипотезы, которые не подтвердились, — это плюс, а не минус.
