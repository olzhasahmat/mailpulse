# Решения

Каждое решение: что выбрали, почему, что рассматривали и чем за это платим. Новые — в конец.

## ADR-001. LangGraph для оркестрации

**Решение.** Обработка письма — граф LangGraph с чекпоинтером в Postgres.

**Почему.** Процесс детерминированный: проверки → классификация → ветвление по важности → ожидание человека. Нужны явные ветвления, цикл правок и пауза на часы между «прислал черновик» и «нажал Отправить». У LangGraph это `interrupt()` + чекпоинтер из коробки.

**Альтернативы.** CrewAI — про команды агентов с ролями, у нас конвейер без свободного диалога агентов. Parlant — про диалоговые гайдлайны, у нас нет чата. Свой конечный автомат — пришлось бы писать сохранение состояния и возобновление самому.

**Цена.** Зависимость от API LangGraph; узлы должны быть готовы к повторному выполнению после resume (ADR-008).

## ADR-002. Один Postgres для данных, векторов, очереди и чекпоинтов

**Решение.** pgvector вместо отдельной векторной БД, очередь на `FOR UPDATE SKIP LOCKED` вместо Redis/Celery.

**Почему.** Один компонент в эксплуатации. Письмо и задача на его обработку пишутся в одной транзакции: не бывает письма без задачи и задачи без письма. Объём (тысячи писем в день на пользователя) далёк от пределов Postgres.

**Альтернативы.** Qdrant — лучше при миллионах векторов и сложной фильтрации; вернёмся, если A/B покажет выигрыш в retrieval. Celery + Redis — ещё два сервиса и нет транзакционности с данными.

**Цена.** Очередь без приоритетов и расписаний; при росте нагрузки polling нагружает базу.

## ADR-003. psycopg 3 как единственный драйвер

**Решение.** SQLAlchemy (async), Alembic и чекпоинтер LangGraph работают через psycopg 3.

**Почему.** Чекпоинтер LangGraph требует psycopg; второй драйвер (asyncpg) — лишняя зависимость и два набора особенностей.

**Цена.** asyncpg быстрее на больших выборках; для нашей нагрузки несущественно.

## ADR-004. Anthropic SDK напрямую, без LangChain chat models

**Решение.** Узлы вызывают Claude через официальный SDK, трейсинг — через обёртку LangSmith.

**Почему.** Узлы LangGraph — обычные функции. Новые возможности API (effort, structured outputs, Batch API, кэширование промптов) в SDK доступны сразу, без ожидания адаптера.

**Цена.** Смена провайдера — реализация порта, а не смена строки конфигурации.

## ADR-005. Единый IMAP-коннектор для всех провайдеров

**Решение.** Gmail (пароль приложения), Microsoft 365 (XOAUTH2) и остальные ящики — через IMAP; отличается только способ входа.

**Почему.** Один код синхронизации для всех ящиков. Для Microsoft OAuth нужен в любом случае, поэтому Graph API не экономит работу.

**Альтернативы.** Gmail API + Microsoft Graph: push-уведомления и нативные треды, но два разных коннектора и модерация scope'ов.

**Цена.** Треды собираем сами по `Message-ID` / `References`; мгновенность только через IDLE, одно соединение на ящик.

## ADR-006. Состояние графа — JSON-совместимые TypedDict

**Решение.** В состоянии только TypedDict, списки и примитивы; Pydantic — на границах (ответы LLM, MCP).

**Почему.** Состояние сериализуется в чекпоинтер между прерываниями. Произвольные классы там ломаются при обновлении кода и требуют разрешений на десериализацию.

## ADR-007. Узлы зависят от портов, реализации передаются через контекст

**Решение.** Все внешние зависимости узлов — Protocol'ы в `agent/ports.py`, передаются через `context` LangGraph.

**Почему.** Граф тестируется фейками без сети и LLM. LLM-реализации сравниваются в A/B подменой одного порта.

## ADR-008. Отправка и ожидание — разные узлы

**Решение.** `send_card` / `await_action` и `send_draft_card` / `review_draft` разделены.

**Почему.** После resume узел с `interrupt()` выполняется заново с начала; отправка в том же узле дублировала бы сообщения в Telegram.

## ADR-009. Нажатия в Telegram возобновляют граф через очередь

**Решение.** Бот только ставит задачу `resume_email`; граф возобновляет воркер.

**Почему.** Бот отвечает на нажатие мгновенно, а LLM-вызовы, ретраи и лимиты живут в одном процессе. Падение бота не теряет решение пользователя.

**Цена.** Задержка между нажатием и следующим сообщением — до интервала опроса очереди (2 с).

## ADR-010. Одобрение отправки проверяется на сервере

**Решение.** Отправить можно только черновик в статусе `approved`, а выставляет его только нажатие «Отправить» в Telegram.

**Почему.** Письмо от постороннего — недоверенный ввод, который читает агент с правом отправки. Запрет в промпте обходится prompt injection; проверку в коде — нет.

## ADR-011. Skills — стандартный SKILL.md и свой загрузчик

**Решение.** Skills в формате Agent Skills; агент подгружает тело Skill'а только в промпт нужного узла.

**Почему.** Один и тот же Skill работает в Claude Code / Desktop и в нашем агенте. Инструкции попадают только туда, где нужны, — меньше токенов в каждом вызове.

**Альтернативы.** Skills через Claude API в контейнере с code execution: наши Skills — инструкции без скриптов, контейнер добавил бы задержку и стоимость на каждое письмо.

## ADR-012. Полнотекстовый поиск с конфигурацией `simple`

**Решение.** `to_tsvector('simple', …)` без стемминга.

**Почему.** Письма смешивают русский, казахский и английский; стеммер одного языка портит остальные. Морфологию закрывает векторный поиск, полнотекст нужен для точных совпадений: номера счетов, фамилии, артикулы.

## ADR-013. Перечисления в БД — VARCHAR

**Решение.** Enum'ы хранятся как VARCHAR, а не нативные типы Postgres.

**Почему.** Новое значение не требует `ALTER TYPE` в миграции.

## ADR-014. Гиперпараметры: temperature на Haiku, effort на Sonnet и Opus

**Решение.** Эксперименты с `temperature` — на узле классификации (Claude Haiku 4.5). На Sonnet 5 и Opus 5 подбираем `effort` и `max_tokens`.

**Почему.** В Sonnet 5 и Opus 5 параметры `temperature`, `top_p`, `top_k` убраны, запрос с ними возвращает 400; глубину и расход токенов задаёт `effort`.

**Как.** В anthropic SDK 1.x у `messages.create` нет аргументов `temperature` и `top_p`. Для Haiku 4.5, который их принимает, они передаются через `extra_body`.

## ADR-015. Приём почты — отдельный сервис в одном экземпляре

**Решение.** IMAP IDLE держит сервис `ingest`, а не воркер.

**Почему.** Воркеров может быть несколько, а соединение с ящиком должно быть одно: копии дублировали бы IDLE и нагрузку на почтовый сервер. Письмо и задача `process_email` записываются в одной транзакции, поэтому приём и разбор масштабируются независимо.

**Цена.** Ещё один процесс; при падении `ingest` новые письма ждут перезапуска (Docker перезапускает сам), а пропущенное догоняется по UID.

## ADR-016. Structured output через `messages.create`, трейсинг вручную

**Решение.** Ответы LLM описаны Pydantic-моделями. Схема преобразуется тем же `transform_schema`, что внутри `messages.parse()`, запрос идёт через `messages.create`, ответ валидируется нашим кодом. Вызов оборачивается в `@traceable(run_type="llm")`, токены передаются в LangSmith как `usage_metadata`.

**Почему.** Готовая обёртка `langsmith.wrappers.wrap_anthropic` (langsmith 0.12) падает на anthropic 1.x: обращается к удалённому `client.completions`. Ручной `@traceable` не зависит от внутренностей SDK. Своя валидация даёт одну ошибку `LlmOutputError` на отказ, обрыв и ответ не по схеме.

**Цена.** Импорт из приватного модуля SDK; версия закреплена в `uv.lock`, контракт проверяет `tests/test_llm.py`. Тесты на фейковом клиенте не ловят несовместимость с настоящим SDK, поэтому в `tests/test_llm.py` есть проверки сигнатуры `messages.create` и сборки настоящего клиента.

## ADR-017. Prompt caching для классификации не используем

**Решение.** Кэширование промпта в узле `classify` не включено.

**Почему.** У Claude Haiku 4.5 кэшируется только префикс длиннее 4096 токенов, а системный промпт классификации (Skill + примеры) короче. Короткий префикс молча не кэшируется. Для узлов на Sonnet 5 порог 1024 токена — там кэширование вернётся вместе с RAG-контекстом.

**Цена.** Оценка стоимости из плана пересчитана: главный рычаг экономии на классификации — Batch API для рассылок и обрезка тела письма, а не кэш.

## ADR-022. Импорт архива индексирует, но не классифицирует

**Решение.** `make import-archive` подтягивает письма за N дней (по умолчанию 90) из INBOX и «Отправленных» обоих ящиков. Письма сохраняются, попадают в треды, историю отправителей и RAG-индекс, но по ним не запускается классификация и не шлются карточки (`save_message(enqueue_processing=False)`).

**Почему.** Правило Skill «пользователь регулярно отвечает этому адресу» и похожие письма в контексте работают только при наполненной истории. Классифицировать архив нельзя: это сотни карточек постфактум и лишние деньги на LLM. Индексацию делает воркер в фоне (задачи `index_email`), поэтому импорт не блокирует приём новой почты.

**Как.** Перед скачиванием тел писем импорт берёт по ENVELOPE только Message-ID и пропускает уже сохранённые — повторный запуск дёшев. Курсор `mailbox_sync` импорт не трогает: он идёт в прошлое, а живой приём — вперёд.

**Цена.** Эмбеддинги архива считаются на CPU (~2 с на письмо в контейнере): 90 дней личного ящика — сотни писем, порядка 10–20 минут фоновой работы. Тела писем скачиваются один раз.

## ADR-023. Вложения: форматный парсинг, vision только для сканов

**Решение.** Текст вложений извлекается по типу: текстовый слой PDF (pypdf), DOCX (python-docx), HTML (bs4), plain text — офлайн, без LLM. Картинки и PDF без текстового слоя идут в мультимодальную модель Claude (Sonnet 5): изображение как `image`-блок, PDF как `document`-блок. Результат и способ (`text_layer`/`docx`/`html`/`vision`/`none`) кэшируются в `attachments`, повторно vision не вызывается.

**Почему.** Это обязательная мультимодальность и реальный сценарий: счёт приходит сканом, и сумма со сроком есть только на картинке — без OCR они не извлекаются вообще. Vision дорогой (~$0.005–0.006 за вложение) и медленный, поэтому запускается только когда текстового слоя нет. Извлечённый текст идёт и в классификацию, и в RAG, и в guardrail — инъекция, спрятанная в PDF, ловится там же, где инъекция в теле письма.

**Цена.** Ещё две зависимости (pypdf, python-docx) и расходы на vision для сканов. Vision-выход — это тоже недоверенные данные (картинка может содержать инструкции), поэтому он проходит через neutralize и guardrail наравне с телом письма.

## ADR-024. Черновики ответов и human-in-the-loop

**Решение.** У писем, требующих ответа, в карточке есть кнопка «✍️ Ответить». Она возобновляет граф: `draft_reply` (Claude Sonnet 5 по Skill reply-drafting) → черновик в Telegram → `review_draft` с кнопками «Отправить / Изменить / Отмена». «Изменить» переводит бота в режим правки: следующий текст пользователя становится указанием, граф генерирует новый черновик (до 3 итераций). «Отправить» помечает черновик approved и отправляет его по SMTP в исходный тред.

**Почему.** Отправка письма от лица пользователя — необратимое внешнее действие, поэтому каждый ответ подтверждается человеком (это и есть human-in-the-loop). Skill запрещает выдумывать факты: на письмо «подтвердите участие» первый черновик — это `[уточнить: …]`, а решение пользователь добавляет через правку. Так модель не соглашается и не отказывается за пользователя.

**Безопасность.** SMTP-отправка идёт только из статуса approved (проверка и в `review_draft`, и в самом `SmtpOutbox`). Тестовые письма (is_test) наружу не уходят: черновик помечается отправленным без SMTP — это позволяет прогонять весь цикл, включая «Отправить», не рассылая писем третьим лицам. Порт 465 → SSL, 587 → STARTTLS; работает для Gmail и Яндекса.

**Цена.** Черновик — вызов Sonnet 5 (~$0.002), каждая правка — ещё один. Режим правки хранится в памяти бота (одна реплика), при рестарте теряется — пользователь просто нажмёт «Изменить» заново.

## ADR-025. MCP-сервер на реальной почте, scoped по пользователю

**Решение.** MCP-сервер работает через `PostgresMailbox`, все запросы скоупятся по `user_id` (join через `mail_accounts`). Для stdio (Claude Desktop / Code на машине пользователя) user_id определяется автоматически, если пользователь один, иначе — из `MCP_USER_ID`. Поиск — ILIKE по теме, отправителю и телу (все слова запроса), без загрузки модели эмбеддингов в процесс MCP. Тестовые письма (is_test) через MCP не видны.

**Почему.** Один и тот же сервер использует и наш агент, и Claude Desktop — пользователь спрашивает «что бухгалтер писал про счёт в сентябре» и получает ответ по своей почте. Скоуп по user_id обязателен: иначе один пользователь увидел бы чужие письма. Эмбеддинги в MCP-процесс не тянем (2 ГБ) — для интерактивного поиска хватает ILIKE; семантический поиск остаётся у агента.

**Безопасность.** `send_draft` отправляет только черновик в статусе approved, а approved ставит лишь нажатие «Отправить» в Telegram. Черновик, созданный через MCP (`create_draft`), остаётся pending и карточки в Telegram не порождает, поэтому одобрить его нельзя — Claude Desktop физически не может отправить письмо без человека. HTTP-транспорт пока без авторизации и слушает только localhost; токены появятся с Mini App (день 9).

**Цена.** ILIKE-поиск без ранжирования по релевантности и без учёта морфологии — для интерактивного поиска по личному ящику достаточно, но не заменяет RAG.

## ADR-026. Mini App: вход через подпись Telegram, фронт из api

**Решение.** Фронтенд — Telegram Mini App (React + Vite). Пользователь определяется по `initData`: клиент шлёт его в заголовке `Authorization: tma <initData>`, сервер проверяет подпись (HMAC-SHA256 секретом из токена бота) и по `user.id` находит или создаёт пользователя. Собранный `miniapp/dist` раздаётся из сервиса `api` на том же адресе, что и `/api`.

**Почему.** Telegram-аккаунт нельзя вводить вручную: бот не может писать по username, а введённый чужой username увёл бы чужие письма (эту дыру мы обсуждали для CLI). Подпись `initData` доказывает личность криптографически. Один контейнер `api` и для API, и для статики — меньше движущихся частей, чем отдельный фронт-сервер; CORS открыт, потому что аутентификация идёт подписанным initData, а не cookie.

**Цена.** Mini App работает только по HTTPS — для разработки нужен туннель, для прода деплой. `initData` действует ограниченное время (проверяем возраст), при устаревании пользователь переоткрывает приложение. Microsoft-ящики в форме пока нельзя (нужен OAuth). CLI `mailpulse-accounts` остаётся для отладки.

## ADR-018. Треды и история переписки собираются при приёме письма

**Решение.** Тред определяется по `In-Reply-To` / `References` среди писем всех ящиков пользователя. Если заголовков нет, а тема начинается с «Re:» / «Ответ:», письмо присоединяется к треду с той же темой за последние 30 дней. Папка «Отправленные» синхронизируется вместе с INBOX, а профиль отправителя (сколько писем пришло, на сколько пользователь ответил) обновляется в той же транзакции.

**Почему.** Правило Skill «пользователь регулярно отвечает этому адресу — важность не ниже 2» не работает, пока модель не видит историю. Считать её при каждом письме запросом к архиву дороже, чем поддерживать счётчики.

**Альтернативы.** Треды только по заголовкам — ломаются на клиентах, которые их не ставят. Склейка по теме без ограничения по времени — склеивает разные «Счёт на оплату».

**Цена.** Отправленные письма синхронизируются при пробуждении IDLE (новое входящее или раз в 9 минут), а не мгновенно. Копия письма, пришедшая в два ящика, хранится дважды, но разбирается и учитывается в истории один раз.

## ADR-019. Эмбеддинги — multilingual-e5-large локально через fastembed

**Решение.** Эмбеддинги считает `intfloat/multilingual-e5-large` (1024 измерения) в воркере через fastembed (ONNX Runtime, без PyTorch). Поиск гибридный: pgvector (cosine) и полнотекстовый поиск Postgres, списки сливаются через RRF (k = 60), в выдаче по одному лучшему чанку на письмо. В промпт классификации попадают до 3 предыдущих писем треда и до 3 похожих писем с пометкой источника.

**Почему.** В плане стояла `bge-m3`, но в fastembed её нет, а ради неё пришлось бы тянуть PyTorch (гигабайты в образе). `jina-embeddings-v3` под лицензией CC-BY-NC — только некоммерческое использование. `multilingual-e5-large` — MIT, около 100 языков, включая русский и казахский. Замеры на CPU (Mac, 8 ядер): загрузка модели 5,5 с, пик памяти ~850 МБ, 0,5 с на фрагмент при пакете из 16 штук, 0,3 с на поисковый запрос. В Docker-контейнере (лимит 4 ядра) эмбеддинг одного запроса — около 2 с; из времени узла retrieve это ~2 с эмбеддинг и ~0,1 с сам поиск в БД. На фоне классификации (Haiku ~4–6 с) и саммари (Sonnet ~3 с) это приемлемо; если понадобится ускорить — модель поменьше или отдельный сервис эмбеддингов. Полнотекстовый поиск нужен для точных совпадений — номера счетов, фамилии, суммы.

**Альтернативы.** Voyage AI по API — без нагрузки на CPU, но это ещё один ключ и внешняя зависимость; остаётся кандидатом для A/B на день 11. Модели на 384–768 измерений легче, но заметно хуже на русском.

**Цена.** Модель весит 2,2 ГБ и скачивается один раз в `./data/models`. Индексация архива из 2 000 писем на CPU займёт около 20 минут. e5 требует префиксов `query:` и `passage:` — fastembed их не ставит, это делает наш адаптер. Смена модели на другую размерность — миграция и переиндексация.

## ADR-020. Порог расстояния 0.18 для похожих писем (заменено ADR-021)

**Решение.** В контекст классификации попадают только похожие письма с косинусным расстоянием до запроса не больше 0.18.

**Почему.** Поиск всегда возвращает «ближайшее», даже если ничего релевантного нет. На оценке (EVALS.md, раздел «Поиск») релевантные письма лежат на расстоянии 0.09–0.23 (медиана 0.13), а первые результаты запросов без ответа — от 0.181. Порог 0.18 оставляет 90% релевантного и не пропускает ни одного нерелевантного результата.

**Цена.** Часть далёких, но релевантных писем (10% на оценке) в контекст не попадёт. Порог подобран на небольшом наборе и привязан к модели: при смене эмбеддингов его нужно подбирать заново через `make eval-retrieval`.

## ADR-021. Три правила отсечения похожих писем

**Решение.** Похожее письмо попадает в контекст классификации при трёх условиях:
- текст письма не короче 30 символов;
- расстояние до запроса хуже лучшего результата не больше чем на 0.03;
- расстояние не больше 0.17.

Значения лежат в `agent/adapters/retriever.py`, и `make eval-retrieval` оценивает именно их.

**Почему.** Порог 0.18 из ADR-020 на настоящей почте пропускал короткие письма («Проверка связи», уведомление о пароле): у e5 такие тексты близки к любому запросу. После добавления в оценочный набор 17 писем-ловушек порог 0.18 давал одно лишнее письмо на запрос и ложный контекст у 30% запросов без ответа. Лучшее из 330 сочетаний трёх правил даёт recall@3 = 0.83 при шуме 0.27 и без ложного контекста. На 5 настоящих письмах все связанные письма остались, все лишние отсеклись.

**Цена.** recall@3 ниже, чем без правил (0.83 против 0.95): часть далёких релевантных писем в контекст не попадёт. Короткое, но важное письмо («Да, согласен») как похожее отсекается; в контекст оно попадёт только через историю треда, где правил нет. Значения привязаны к модели эмбеддингов и подобраны на небольшом наборе.
